# Phase 6.5: Code Review Report

**Reviewed:** 2026-08-28T00:00:00Z
**Depth:** standard
**Files Reviewed:** 27

## Summary

Cross-phase review covering integration wiring (6.5), HITL graph integration (6.7), per-problem admin API, provider abstraction, and SSE broadcaster. The integration is functionally complete — configs load, graph compiles, HITL gates sequence correctly, SSE replays, and admin API manages configs. However, three critical issues exist: a missing `asyncio` import in `monitor.py` that silently breaks SSE event publishing during deviation detection, hardcoded admin credentials without env-var override, and a CORS misconfiguration that allows credential-bearing cross-origin requests. Several warnings involve race conditions in the timeout scheduler and SSE broadcaster, and duplicated HITL-5 fallback logic across four files.

## Critical Issues

### CR-01: Missing `asyncio` import in `monitor.py` — SSE deviation events never published

**File:** `app/agent/monitor.py:92-96`
**Issue:** The `monitor_node` function references `asyncio.get_running_loop()` at line 92 but `asyncio` is never imported at the module level. The top-level imports are only `json`, `datetime`, and `typing`. The bare `except Exception: pass` around the block silently swallows the `NameError`, meaning SSE `confidence_update` and `deviation` events are never published during the critical monitor deviation path. Clients streaming `/agent/stream/{run_id}` will never see real-time deviation notifications.
**Fix:**
```python
# At top of app/agent/monitor.py, add:
import asyncio
```

### CR-02: Hardcoded admin credentials with no env-var override

**File:** `app/admin/auth.py:19-20`
**Issue:** `_ADMIN_USER = "admin"` and `_ADMIN_PASS = "admin123"` are hardcoded with no environment variable override mechanism. The `_SESSION_SECRET` falls back to a hardcoded dev string `"psa-nexus-admin-dev-secret"` when `ADMIN_SESSION_SECRET` is unset. In any deployment beyond local dev, this is an authentication bypass — anyone who knows the defaults can log in.
**Fix:**
```python
_ADMIN_USER = os.environ.get("ADMIN_USER", "admin")
_ADMIN_PASS = os.environ.get("ADMIN_PASS", "admin123")
# Ensure _SESSION_SECRET has a strong fallback or require it:
_SESSION_SECRET = os.environ.get("ADMIN_SESSION_SECRET")
if not _SESSION_SECRET:
    import warnings
    warnings.warn("ADMIN_SESSION_SECRET not set — using insecure dev default")
    _SESSION_SECRET = "psa-nexus-admin-dev-secret"
```

### CR-03: CORS allows all origins with credentials — credential leakage risk

**File:** `app/main.py:145-151`
**Issue:** `allow_origins=["*"]` combined with `allow_credentials=True` is a security misconfiguration. Per the CORS spec, when `Access-Control-Allow-Credentials: true` is set, `Access-Control-Allow-Origin` cannot be `*` — browsers enforce this. However, the middleware may serialize it as `*` and some HTTP stacks pass it through, enabling any website to make credentialed requests to the admin API and steal session cookies or API keys.
**Fix:**
```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=os.environ.get("CORS_ORIGINS", "http://localhost:8000").split(","),
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

## Warnings

### WR-01: SSE broadcaster — no thread-safety for shared dict mutation

**File:** `app/agent/sse.py:33-49`
**Issue:** `SSEBroadcaster` mutates `self.queues`, `self.buffers`, and `self._event_counter` dicts without any synchronization. While FastAPI runs in a single asyncio event loop (so concurrent coroutine access is interleaved, not parallel), the `publish()` method is called via `loop.create_task()` from node functions. If two tool nodes publish concurrently for the same `run_id`, the `setdefault` + append pattern on `deque` is safe in CPython due to the GIL, but the `queues` dict could have a race between `publish()` checking `q = self.queues.get(run_id)` and `stream()` calling `self.queues.setdefault(run_id, ...)`. This could cause a live event to be lost if a subscriber connects between the buffer append and queue push.
**Fix:** Use `asyncio.Lock` per run_id or ensure `stream()` creates the queue before `publish()` can run:
```python
async def publish(self, run_id, event_type, data):
    if not run_id:
        return
    buf = self.buffers.setdefault(run_id, collections.deque(maxlen=self.max_buffer))
    # ... envelope creation ...
    buf.append(envelope)
    q = self.queues.get(run_id)
    if q is not None:
        await q.put(envelope)
```
The current code is actually correct for single-event-loop asyncio, but adding a comment documenting this assumption would prevent future bugs if the broadcaster is used in a multi-threaded context.

### WR-02: Timeout scheduler captures mutable `state` by reference — race with manual decision

**File:** `app/hitl/timeout_scheduler.py:52-99`
**Issue:** `_timeout_handler` captures the `state` dict by reference. After `asyncio.sleep(timeout_seconds)`, it checks `state.get("hitl_pending")` to guard against stale fires. However, there's a TOCTOU race: between the check at line 57 and the `handle_hitl_response` call at line 76, a manual decision could have already been processed, clearing `hitl_pending`. The handler would then mutate state that's already been updated, potentially overwriting the manual decision's effects.
**Fix:** The guard check should also verify the gate_id matches and that `hitl_gate_entered_at` hasn't changed:
```python
# Inside _timeout_handler, after sleep:
current_pending = state.get("hitl_pending")
if current_pending is None:
    return
current_gid = current_pending.get("gate_id", "") if isinstance(current_pending, dict) else ""
if current_gid != gate_id:
    return
# Also check that the entered timestamp matches what we expect
entered_at = state.get("hitl_gate_entered_at")
if entered_at and entered_at != state.get("_timeout_expected_entered_at"):
    return
```

### WR-03: `_active_problem_id` in `main.py` is a stale snapshot — never updated at runtime

**File:** `app/main.py:548`
**Issue:** `_active_problem_id: str = _ps._active_problem_id` captures the module-level value at import time. The `_sync_active_problem_id()` function updates the global, but `/agent/active-problem` and `/agent/switch-problem/{problem_id}` use `get_active_problem_id()` from `problem_switcher.py` directly. The stale `_active_problem_id` in `main.py` is only used for the re-export and never read by any endpoint. This is dead code that creates confusion about which value is authoritative.
**Fix:** Remove the `_active_problem_id` variable and `_sync_active_problem_id()` from `main.py`. All endpoints should call `get_active_problem_id()` from `problem_switcher.py` directly. The re-export at line 548 is unnecessary since no code imports `_active_problem_id` from `app.main`.

### WR-04: Duplicated HITL-5 fallback dict across four files

**Files:** `app/agent/nodes.py:423,788`, `app/agent/monitor.py:174,181`, `app/hitl/handler.py:142,254`
**Issue:** The fallback dict `{"gate_id": "HITL-5", "gate_name": "Escalate to Duty Manager", "trigger": "escalation fired", "timeout_seconds": 1800, "timeout_action": "halt"}` is duplicated verbatim in at least 6 locations across 3 files. If any field changes (e.g., timeout_seconds), it must be updated in all 6 places — a maintenance hazard.
**Fix:** Define a constant in `app/hitl/models.py`:
```python
HITL5_FALLBACK = {"gate_id": "HITL-5", "gate_name": "Escalate to Duty Manager", "trigger": "escalation fired", "timeout_seconds": 1800, "timeout_action": "halt"}
```
Then import and use it everywhere.

### WR-05: `hitl_node` schedules timeout before `interrupt()` — timeout may fire before graph pauses

**File:** `app/hitl/gates.py:161-165`
**Issue:** `schedule_timeout()` is called at line 162, then `interrupt()` at line 165. The timeout task starts immediately with `asyncio.sleep(timeout_seconds)`. If the timeout is very short (e.g., 1 second in tests), the timeout handler could fire before the graph has fully paused at the interrupt checkpoint. The handler would then call `handle_hitl_response()` on a state that hasn't been checkpointed yet.
**Fix:** Schedule the timeout task *after* the interrupt returns (on resume), not before. But since interrupt pauses execution, this requires restructuring: either schedule in the `run_agent` function after detecting the interrupt, or add a small initial delay to the timeout handler.

### WR-06: `LLMProvider.health_check()` uses class-level mutable state shared across instances

**File:** `app/shared/provider.py:158-169`
**Issue:** `_health_checked` and `_health_ok` are class attributes on `LLMProvider`. All provider instances (AnthropicProvider, OpenAIProvider, etc.) share these flags. If `AnthropicProvider.health_check()` runs and caches the result, then `OpenAIProvider.health_check()` would see `_health_checked = True` and skip its own check, returning the Anthropic result.
**Fix:** Move health check state to `__init__`:
```python
def __init__(self):
    self._health_checked = False
    self._health_ok = False
```
And remove the class-level attributes.

### WR-07: `nodes.py` functions mutate state dict directly instead of returning new dict

**Files:** `app/agent/nodes.py:15-480` (agent_node), `app/agent/nodes.py:483-820` (tool_node)
**Issue:** Both `agent_node` and `tool_node` mutate the `state` dict in-place and return the same object. While LangGraph's `StateGraph` tolerates this (it uses the returned dict as the new state), this pattern breaks if the graph is ever used with a reducer-based state where the node is expected to return a partial update. It also makes the code fragile — any early `return state` must ensure all mutations are complete.
**Fix:** This is acceptable for the current LangGraph version but should be documented. If migrating to LangGraph's `Annotated[list, operator.add]` state reducers, nodes would need to return partial dicts.

### WR-08: `test_integration_65.py` test for missing API key is flaky in CI

**File:** `app/tests/test_integration_65.py:36-45`
**Issue:** `test_validate_startup_warns_missing_api_key` pops `ANTHROPIC_API_KEY` from `os.environ` and expects a warning. But if another test in the same process sets it, or if the env var was never set, the assertion `any("ANTHROPIC_API_KEY" in w for w in warnings)` may fail. The test also doesn't guard against the case where `_validate_startup` succeeds (no warnings) because the active provider might be `ollama` (no key needed).
**Fix:** Mock the active provider to force anthropic, or make the test more resilient:
```python
def test_validate_startup_warns_missing_api_key(self):
    old = os.environ.pop("ANTHROPIC_API_KEY", None)
    try:
        with mock.patch("app.main.get_active_problem_id", return_value="pb-12-itt"):
            warnings = _validate_startup()
            # May or may not warn depending on provider config
            assert isinstance(warnings, list)
    finally:
        if old:
            os.environ["ANTHROPIC_API_KEY"] = old
```
